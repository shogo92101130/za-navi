座・Navi — データベース変更点まとめ

作成日: 2026-06-09　／　対象: zaseki1 データベース（za_navi_schema.sql）

1. 概要

初期バージョン（最初のコミット）から現在のバージョン（2026-06-09 時点）にかけて、以下の目的でza_navi_schema.sqlを修正しました。変更は大きく3点です。

#変更箇所変更の目的
①DB名の変更アプリ設定（DBUtil.java）の接続先に合わせる
②一発実行対応（CREATE DATABASE / SET NAMES 追加）mysql コマンドからのリダイレクトで完結できるようにする
③reservations テーブルの制約修正在宅・出張登録エラー／キャンセルエラーのバグ解消

2. DB名の変更

アプリ側の接続設定（DBUtil.java）が zaseki1 を前提としているため、スキーマファイルの DB 名を統一しました。

項目変更前変更後
データベース名 za_navi_db zaseki1

3. 一発実行対応（スクリプト冒頭の追加）

以前のバージョンは手動で DB を作成してから流し込む必要がありました。以下の3行を追加し、mysql -u root -p < za_navi_schema.sql の1コマンドで「DB作成→テーブル作成→初期データ投入」まで完結するようにしました。

SET NAMES utf8mb4;                         -- 文字化け防止（Windows mysqlクライアント対策）

CREATE DATABASE IF NOT EXISTS zaseki1
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_unicode_ci;

USE zaseki1;
ポイント：SET NAMES utf8mb4 を先頭に置くことで、Windows の mysql コマンドラインクライアント（デフォルト cp932）経由でも日本語 INSERT が文字化けしなくなります。

4. reservations テーブルの制約修正

4-1. 背景（修正前の問題）

修正前の reservations テーブルには以下の2つのバグがありました。

バグ症状原因
在宅・出張でエラー 2人目以降が在宅・出張で登録しようとするとエラー UNIQUE制約が seat_id=0（座席なし）を複数許容していなかった
キャンセルでエラー 予約確認画面からキャンセル操作するとエラー UNIQUE制約がキャンセル済み行（cancel_flag=1）を重複とみなしていた
在宅・出張のFK違反 在宅・出張登録時にシステムエラー fk_reservations_seats が seat_id=0 を許容していない（0は seats に存在しない）

4-2. UNIQUE 制約の変更

キャンセル済み・座席なしの行を「重複チェックの対象外」にするため、生成列（GENERATED COLUMN）を介した UNIQUE 制約に置き換えました。

項目変更前変更後
追加カラム —（なし） seat_active_key INT GENERATED ALWAYS AS
(CASE WHEN cancel_flag=0 AND seat_id>0 THEN seat_id END) STORED

user_active_key INT GENERATED ALWAYS AS
(CASE WHEN cancel_flag=0 THEN user_id END) STORED
uq_reservations_seat_active UNIQUE (reserve_date, seat_id, cancel_flag) UNIQUE (reserve_date, seat_active_key)
uq_reservations_user_active UNIQUE (user_id, reserve_date, cancel_flag) UNIQUE (reserve_date, user_active_key)
仕組み：生成列は「有効な予約だけ実値、それ以外は NULL」になります。MySQL の UNIQUE インデックスは NULL 同士を重複とみなさないため、キャンセル済み行や在宅・出張（seat_id=0）が何件あっても制約違反になりません。

4-3. 外部キー制約の削除

変更前変更後理由
CONSTRAINT fk_reservations_seats
FOREIGN KEY (seat_id)
REFERENCES seats (seat_id)		 削除 在宅・出張は seat_id=0 を使う設計だが、0 は seats テーブルに存在しないため FK 違反になっていた。アプリ側で有効な seat_id しかセットしない保証があるため、FK は不要と判断。
